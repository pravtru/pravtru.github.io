# pravtru.github.io

Статический сайт на GitHub Pages — генератор графических элементов инженерной/электротехнической документации по ГОСТ (со ссылкой на СП 333.1325800.2020 для формирования IFC-моделей). Без build-процесса и фреймворков: чистые HTML/JS/XML.

## Структура проекта

- **`index.htm`** — стартовая страница-описание с картой понятий: *Объект → Раздел → Модуль → Элемент → Блок*.
- **`View.html`** — движок рендеринга. Через `?name=XXX` в URL подгружает `XXX.xml`, рекурсивно разворачивает вложенные `<Bl>`/`<Bl0>` (заменяя их содержимым соответствующего XML-файла с подстановкой параметров по `id`/`bid`), выводит итоговый SVG и исходный код на странице. Если в файле несколько тегов `<svg>`, они показываются постранично (кнопки «Назад»/«Вперёд», индикатор страницы с атрибутом `tip`), а не все сразу.
- **`Ob.htm` / `Mdl.htm` / `El.htm` / `Blok.htm`** — описания понятий "Объект", "Модуль", "Элемент" и "Блок", каждое дополнено таблицей-каталогом всех соответствующих XML-файлов со ссылкой "Просмотреть" (`View.html?name=...`) для предпросмотра.
- **XML-файлы в корне проекта** — библиотека графических элементов, разбитая на четыре типа: **Элементы** (`<El>`, каталог в `El.htm`), **Модули** (`<Mdl>`, каталог в `Mdl.htm`) — составная часть объекта из нескольких элементов, **Блоки** (`<Bl>`, каталог в `Blok.htm`) и **Объекты** (записи `<project>` внутри `Projects.xml`, каталог в `Ob.htm`). Полный список — см. ниже.
- **`bootstrap.min.css` / `bootstrap.bundle.min.js`** — вендорные библиотеки для UI (модальные окна выбора модели/параметров в `View.html`).

## Перенос блоков из БД `pravt` (таблица `Bloki`)

На локальном SQL Server есть база `pravt` с таблицей `Bloki` (166 строк, колонки `ID`, `Name`, `XML`, `User`) — более ранняя/параллельная версия этого проекта на собственном векторном DSL (`<Blok Name>`, `<Line Width><Pt X Y H W/></Line>`, `<Arc X Y R sAng Ang/>`, `<Text Size Aligned X Y P R Wmax/>`, ссылки на другие блоки `<Blok ID=N X Y><P ID=M>...</P></Blok>`, условные варианты `<If P="0"><eq>N</eq><Then>...</Then></If>`).

Правила пересчёта в текущий SVG-формат:
- координаты: старая система Y вверх (математическая), SVG — Y вниз → **все Y меняются знаком** (`svg_y = -old_y`);
- `<Line>`/`<Pt>` → `<line>`/`<polyline>`/`<rect>` (или `<polygon fill="#000">`, если исходная толстая линия явно рисует закрашенную фигуru — стрелки, треугольники);
- `<Arc X Y R>` (без sAng/Ang) → `<circle r="R">`; `<Arc ... sAng Ang>` (везде встречались только полуокружности) → приближение квадратичной кривой Безье;
- `<Text ... P="N">` → `id="N"` (цель для `<Pr bid="N">`); `R="90"` → `transform="rotate(-90 x y)"`; `AlY="1"` → `dominant-baseline="middle"`;
- `<Blok ID="N" X Y><P ID="M">текст</P></Blok>` → `<g transform="translate(X Y)"><Bl Name="ИмяПоID"><Pr bid="M">текст</Pr></Bl></g>`.

166 строк делятся на 3 категории: ~120 простых графических блоков, ~22 блока со встроенным `<Script>` (JS, динамически строит форму параметров и генерирует схему — прямого аналога в текущей статической системе нет, не переносились), ~20 блоков с именами-числами (`"5"`…`"23"`) — сохранённые листы конкретного проекта, а не переиспользуемые шаблоны.

Перенос простых блоков и блоков-чисел завершён (94 файла, все без `<Script>`):
- **Первая партия (16 файлов)**: `Klemma.xml`, `KlemmaWide.xml`, `ChainNumber.xml`, `Rele_Time.xml`, `Perekl2.xml`, `Perekl3.xml`, `PriborSA.xml`, `NasosSA.xml`, `TreugolnikSA.xml`, `VozvratnikSA.xml`, `AI_SA.xml`, `DI_SA.xml`, `Ethernet_SA.xml`, `Zadvizhka.xml`, `UPS.xml`, `PLC_Rele.xml`.

## Только типовые объекты

В проекте хранятся только типовые объекты многократного применения: блоки, элементы, модули и настраиваемые объекты. Листы и схемы конкретных проектов сюда не добавляются — они хранятся в данных проекта (формат EPX), а отсюда берут изображения типовых объектов.

## Связь с данными проектов (формат EPX)

Конкретные объекты проектов хранятся отдельно, в формате EPX, а отсюда берут типовые объекты:

- **`TPL`** (в EPX) — ссылка части объекта на типовой объект этой библиотеки: имя файла без `.xml`, например `<TPL>Privod_Auma</TPL>`. Изображения части на схемах и её выводы берутся из типового объекта.
- **`VIEW`** (в EPX) — на какой схеме проекта изображена часть: `TYPE` — вид схемы, `REF` — `id` листа проекта (`SHT`), `XY` — точка вставки изображения в мм листа (ось Y вниз, как в SVG), `ROT` — поворот в градусах против часовой стрелки. Вид схемы соответствует изображению элемента `<svg tip>`: схема автоматизации — `SA`, схема принципиальная — `SP`, схема внешних соединений — `SV`, план — `PL`, схема технологическая — `TS`.
- **`ALIAS`** (здесь, внутри `El` и `Mdl`, повторяется) — синоним для распознавания: имя блока DWG (совпадает полностью) или начало марки из спецификации. При сравнении не учитываются регистр, пробелы и дефисы; одинаковые по виду кириллические и латинские буквы (А/A, С/C, Е/E, К/K, М/M, Н/H, О/O, Р/P, Т/T, Х/X, В/B) считаются одной буквой; запятые и точки значимы. По синонимам при сборке данных EPX заполняется `TPL`, а разбор схем узнаёт оборудование.

```xml
<El Name="Электропривод задвижки Auma">
  <ALIAS>Auma</ALIAS>
  <ALIAS>привод_auma</ALIAS>
  ...
</El>
```

Свойства элемента записываются теми же тегами, что и в EPX (вместо прежнего пустого `<Elem>`), перед изображениями `<svg>`:

| Тег | Что хранит |
|---|---|
| `TYPE` | вид: насос, прибор, арматура, электроаппарат, щит, агрегат и т. д. |
| `MARK` | тип, марка |
| `MAKER` | изготовитель |
| `UNIT` | единица измерения |
| `PRM` | постоянная характеристика изделия: цвет линзы, ток, мощность, Ду; повторяется |
| `FUNC` | для приборов — код по ГОСТ 21.208 |
| `MED` | для арматуры и насосов — рабочая среда |
| `PIN` | вывод изделия, повторяется; номера совпадают с выводами в цепях модулей |

```xml
<El Name="Магнитный пускатель DILM7/21">
 <TYPE>электроаппарат</TYPE>
 <MARK>DILM7/21</MARK>
 <UNIT>шт</UNIT>
 <PIN>1</PIN> <PIN>2</PIN> … <PIN>A1</PIN> <PIN>A2</PIN> <PIN>21</PIN> <PIN>22</PIN> <PIN>33</PIN> <PIN>34</PIN>
 <svg tip="SP" …>…</svg>
</El>
```

Сведения заполняются только из документов: выводы 12 элементов реверсивного привода взяты с листа 5, марки — со спецификации листа 6 «Пример.pdf»; если в источнике сведений нет (выводы автоматов и ламп, изготовители), тег не пишется.

## Шаблон проекта (`Prj`)

По шаблону проекта генератор pdgen (pdgen.ru) собирает комплект документации в PDF. Всё, что отличает один проект от другого, описывается здесь, в XML; код pdgen от проекта не зависит.

- **`Prj`** — шаблон проекта, четвёртый вид типового объекта наряду с `Bl`, `El`, `Mdl`; один файл на шаблон. Внутри — параметры `<var>` (`id`, `name`, `type` b/i, `default`, `min`, `max`) и состав `DOCS`/`DOC`/`SHTS`/`SHT` с `CODE`, `SNAME`, `TYPE`, `FMT` (теги формата EPX). Содержимое листа — `<svg tip>` с блоками, элементами и модулями, как в модулях. Документ вида «спецификация оборудования» не рисуется: он собирается из элементов, попавших на листы.
- **Дерево объектов.** Состав шаблона — `OBJS` → `OBJ` → `OBJS` на любую глубину (`SNAME`, `POS`, `MARK`, `QTY`, `UNIT`, `TPL`). Лист не рисуется в шаблоне: генератор обходит дерево и у каждого объекта берёт изображение для вида листа (`<svg tip>` типового объекта: SA, SP, SV, PL, TS); место задаёт `VIEW` с `XY`/`ROT`, без него объекты раскладываются по порядку. В изображениях типовых объектов `{POS}`, `{SNAME}`, `{QTY}` заменяются значениями объекта. Первый шаблон — `Prj_Skvazhina.xml` (артезианская скважина по проекту 27-17-АТХ) с элементами `PLC150_220`, `BKK1_220`, `PD100_DI`, `PD100_DG`, `DS1`, `TER`, `FR_F840`, `M22_WRK3`, `QF_FAZ_C6`, `QF_FAZ_C2`, `UPS_BC500`, `ZI_60_24`, `Nasos_pogr`, `Shchit_ShU`.
- **Выводы и связи.** Точка вывода на изображении элемента отмечается атрибутом `PIN` (значение — как в `<PIN>` элемента), например `<circle cx="-6" cy="5" r="0.8" PIN="L1"/>`. Цепи шаблона (`LNKS`/`LNK`: `TYPE` цепь, `POS` — номер цепи, `FROM`/`TO` с `SNAME` — позицией объекта и `PIN` — выводом) генератор проводит между этими точками на листе, где есть оба конца.
- **`Projects.xml`** — каталог проектов: запись `<project>` (`id`, `name`, `description`) ссылается на шаблон тегом `<TPL>имя файла шаблона без .xml</TPL>`.
- **`IF`** — условие по параметрам на `DOC`, `SHT` и любом узле листа (`g`, `Bl`, `El`, `Mdl`): `IF="vfd=1"`, `IF="levels>=2 flow=1"`. Операции `=`, `!=`, `>`, `>=`, `<`, `<=`; несколько условий через пробел — «и»; для «или» — второй узел. При ложном условии узел не выводится.
- **Подстановки `{…}`** в тексте и атрибутах: `{параметр}` — значение параметра; `{CODE}`, `{FNAME}`, `{STG}`, `{ORG}` — данные проекта, вводимые при генерации; `{SHT}`, `{SHTS}` — номер листа и число листов.

```xml
<Prj Name="Автоматизация артезианской скважины">
 <var id="vfd" name="Управление насосом через ПЧ" type="b" default="1"/>
 <DOCS>
  <DOC>
   <CODE>{CODE}-АТХ</CODE>
   <TYPE>комплект рабочих чертежей</TYPE>
   <SHTS>
    <SHT IF="vfd=1"><SNAME>Подключение насоса через ПЧ</SNAME><TYPE>схема принципиальная</TYPE><FMT>A3</FMT>
     <svg tip="A3" viewBox="0 0 420 297"><Bl Name="A3BS"/>…</svg>
    </SHT>
   </SHTS>
  </DOC>
 </DOCS>
</Prj>
```

## Механизм подстановки блоков

Блок вызывается с параметрами, например:

```xml
<Bl Name="XT1"><Pr bid="1" transform="translate(0 0) rotate(0 0 0)"></Pr></Bl>
```

`View.html` рекурсивно ищет в вызываемом блоке элементы с атрибутом `id`, совпадающим с `bid` переданного параметра `<Pr>`, и заменяет их атрибуты/содержимое — то есть это самодельный шаблонизатор для SVG на чистом JS без зависимостей.
